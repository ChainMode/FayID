# 第 5 章 非リンク型ダイナミックコード、認証交換およびカスケード失効

## 5.1 非リンク型ダイナミックコード（`dyn_`）の発行と検証（Normative）

平文の `hid_` は決して外部送出されないため、**人間プライム**ならびにその配下の `iFay` および `coFay` は、境界を越えてアイデンティティを提示する際に短命かつソルト付きで関連付け不可能なダイナミックコード（`dyn_<base32>`）を使用する。

1. **正当な対象主体**：ダイナミックコードは未失効の `HumanID`（`hid_`）、`iFayID`（`ifay_`）、または `coFayID`（`cofay_`）に対してのみ発行が許可される。`OrganizationID`（`org_`）に対するダイナミックコードの発行要求は拒否し、`DYNAMIC_CODE_TARGET_NOT_ALLOWED` を返さ**なければならない**（`MUST`）（組織識別子自体は公開主体であり、仮名ダイナミックコードを必要としない）。
2. **ソルト付き非リンク構造**：発行ごとに少なくとも 16 バイトの暗号論的乱数 `nonce` を生成し、`ifay.fayid.dynamic-code.v1` ドメイン鍵のもとで正規化ペイロード `{audience, expiresAt, issuedAt, nonceHex, targetId, version: "1.0"}` に対して HMAC-SHA256 を計算し、先頭 20 バイトを切り詰めて `dyn_<base32>` にエンコードする。受動的な盗聴者は、検証コンテキスト鍵を持たない限り、2 回提示された `dyn_` 文字列を観測してもそれらが同一主体に由来するかどうかを判定できない。
3. **厳格な有効期間上限**：`expiresAt - issuedAt` は `0` より大きく、かつ **`600` 秒（`DYNAMIC_CODE_MAX_TTL_SECONDS = 600`）**以下で**なければならない**（`MUST`）。上限を超える発行要求は拒否し、`DYNAMIC_CODE_INVALID` を返さ**なければならない**（`MUST`）。
4. **ワンタイム消費およびリプレイ防止**：検証者が `dyn_` を検証する際は以下の規則に従う。
   - 主体自体またはその上流の帰属主体が失効している場合、拒否して `ENTITY_REVOKED` を返さ**なければならない**（`MUST`）。
   - 検証時刻が `expiresAt` を過ぎている場合、拒否して `DYNAMIC_CODE_EXPIRED` を返さ**なければならない**（`MUST`）。
   - `audience` が一致しない場合（トークンが想定オーディエンスにバインドされているとき）またはトークンが未知である場合、`DYNAMIC_CODE_INVALID` を返さ**なければならない**（`MUST`）。
   - 各 `dyn_` のランダム `nonce` は**1 回のみ**検証・消費が許可される。同一の `dyn_` の 2 回目以降の重複送信は拒否し、`DYNAMIC_CODE_REPLAYED` を返さ**なければならない**（`MUST`）。
5. **検証結果のプライバシー保護**：`dyn_` にバインドされた基底主体が `HumanID` である場合、検証成功レスポンスで呼び出し元に平文の `hid_` を返しては**ならず**、主体種別 `"HUMAN"` およびブラインドソルトから決定論的に派生した `gmcref_<base32>` アンカーを返さ**なければならない**（`MUST`）。

## 5.2 従来型クレデンシャルバインディングと認証交換認可（`grt_` / `vrf_`）（Normative）

Auth Exchange により、保持者は外部既存システムのクレデンシャルをスコープ制限付きの FayID 認可クレデンシャル（`grt_<base32>`）へ安全にブリッジし、リソースアクセス時にオフラインで署名検証可能な検証レシート（`vrf_<base32>`）を生成できる。

1. **従来型サブジェクトのプライバシーハッシュ（`LegacySubjectRef`）**：外部クレデンシャルのサブジェクトは正規化のうえ鍵付き HMAC 処理を施し、`<legacySourceKind>:<issuerOrAuthority>:<subjectHash>` と**しなければならない**（`MUST`）。ここで `subjectHash = base32NoPad(HMAC-SHA256(legacySecret, canonicalSubject))` である。`LegacySubjectRef` に平文のメールアドレス、電話番号、X.509 DN、OAuth 生トークン、またはブロックチェーンの平文ウォレットアドレスを直接連結**してはならない**。
2. **デフォルト信頼レベルマッピング（`LegacyTrustLevel`）**：
   - `PASSWORD` → `LOW`（認可 TTL 上限は **`900` 秒**、`LOW_TRUST_GRANT_MAX_TTL_SECONDS`）
   - `ACCESS_TOKEN`、`AUTHORIZATION` → `MEDIUM`（認可 TTL 上限は **`3600` 秒**、`GRANT_MAX_TTL_SECONDS`）
   - `CERTIFICATE`、`SMART_CONTRACT` → `HIGH`（認可 TTL 上限は **`3600` 秒**）
   実装はリスクポリシーに応じて信頼レベルの引き下げまたは TTL の短縮を行っても**よい**（`MAY`）が、追加の多要素保持者証明なしに信頼レベルを引き上げては**ならない**（`MUST NOT`）。
3. **対象保持証明の優先検査（プローブ防止）**：`grt_` の発行時、対象主体は未失効の `iFayID` または `coFayID` に限定され、要求者は対象主体の保持者署名証明を提示**しなければならない**（`MUST`）。対象の保持証明が欠落または無効である場合、システムは優先的に `TARGET_OWNERSHIP_NOT_PROVEN` を返さ**なければならない**（`MUST`）。これにより、攻撃者がエラーコードの差異から特定の従来型アカウントが特定の FayID にバインド済みかどうかを推測することを防ぐ。
4. **スコープ付き検証および `vrf_` レシートの発行**：`verifyAuthGrant` を呼び出して `grt_` を検証する際、システムは以下の順序で検査を行う。
   - 認可レコードが存在し、構造が正当であること（そうでない場合は `GRANT_INVALID` を返す）。
   - 対象エンティティおよびその上流所有者が失効していないこと（エンティティが失効済みの場合は優先して `ENTITY_REVOKED` を返す）。
   - 認可自体が明示的に失効していないこと（失効済みの場合は `GRANT_REVOKED` を返す）。
   - 現在時刻が `expiresAt` を超えていないこと（超えている場合は `GRANT_EXPIRED` を返す）。
   - 要求された `requestedResourceRef` が第 2.3 節の `scopeMode`（`EXACT` / `PREFIX`）に従って認可の `resourceRef` と一致すること（不一致の場合は `GRANT_INVALID` を返す）。
   すべて通過した後、システムは `ifay.fayid.auth-exchange.v1` ドメインの Ed25519 鍵を用いて正規化された検証結論に署名し、`vrf_<base32>` レシートを返す。任意の第三者は `verifyAuthReceipt(receipt)` を呼び出すことでレシートの署名と構造の完全性を独立して検証でき、いずれかのフィールドが改ざんされている場合は `RECEIPT_INVALID` を返さ**なければならない**（`MUST`）。

## 5.3 決定論的カスケード失効（Cascading Revocation）（Normative）

失効は単調かつ不可逆な終端状態への遷移操作である。いずれかのエンティティが失効した際、システムは直ちに帰属関係および階層関係に従って決定論的にカスケード失効を実行**しなければならず**（`MUST`）、宙に浮いたアクティブな子エンティティやアクティブな認可クレデンシャルを残しては**ならない**。

| 失効の起点となるルートエンティティ | カスケード失効する下流エンティティの範囲 | 運用権限およびアクティブなクレデンシャルに対する必須の付随措置 |
| --- | --- | --- |
| **`HumanID`（`hid_`）** | 当該**人間プライム**配下のすべての `iFay`（`ifay_`）および当該 `hid_` に直接帰属するすべての `coFay`（`cofay_`） | すべての未失効 `coFay.managers` から上記のカスケード失効された `ifay_` を削除し、上記の `ifay_` / `cofay_` を指すすべてのアクティブな `grt_` および未消費の `dyn_` を失効させる |
| **`OrganizationID`（`org_`）** | 当該組織自体、組織階層ツリー内のすべての子孫組織（再帰的サブツリー）、および当該組織またはいずれかの子孫組織に直接帰属するすべての `coFay` | 上記のカスケード失効された `cofay_` を指すすべてのアクティブな `grt_` および未消費の `dyn_` を失効させる |
| **`iFayID`（`ifay_`）** | 当該 `iFay` 自体 | すべての未失効 `coFay.managers` リストから当該 `ifay_` を直ちに削除し、当該 `ifay_` を `targetFayId` とするすべてのアクティブな `grt_` および未消費の `dyn_` を失効させる |
| **`coFayID`（`cofay_`）** | 当該 `coFay` 自体 | 当該 `cofay_` を `targetFayId` とするすべてのアクティブな `grt_` および未消費の `dyn_` を失効させる |

カスケード失効の完了後、以下の規則が適用される。
1. 直接またはカスケードによって失効したエンティティに対する新規 `dyn_` や `grt_` の発行、新規下位エンティティの登録、または既存クレデンシャルの検証は、決定論的に拒否して `ENTITY_REVOKED` を返さ**なければならない**（`MUST`）（対象エンティティは有効なままで個別に手動失効された認可に対しては `GRANT_REVOKED` を返す）。
2. 失効したエンティティのクレデンシャルは、当初の TTL 時間窓内であっても**直ちに無効**となり、検証を通過させては**ならない**。
