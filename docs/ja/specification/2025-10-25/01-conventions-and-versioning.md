# 第 1 章 仕様規約、中核用語およびバージョンガバナンス

## 1.1 適用範囲と非目標

FayID 1.0 は、iFay エコシステム内における自己主権型 ID 識別子、目的別サブ鍵派生、エンティティ所有権と組織階層の不変条件、非リンク型ダイナミックコード、従来型クレデンシャルの認証交換、カスケード失効、および`公誉チェーン`（`GMChain`）向けのプライバシー保護型自然人アンカーを定義する。

以下の事項は明確に本プロトコルの対象外である。

1. **トランスポートおよびセッションハンドシェイクプロトコル**：エージェント間通信のメッセージカプセル化およびセッションセキュリティは Faying プロトコル群によって定義される。FayID はアイデンティティプリミティブ、署名エンベロープ、および検証レシートのみを提供する。
2. **ランタイムライフサイクルスケジューリング**：端末デバイス上における `iFay` および `coFay` のプロセスオーケストレーションは FayGer ランタイムが担う。
3. **レピュテーション記帳およびガバナンス重み計算**：`美誉値`（`MeriToken`）の蓄積およびガバナンス計量は `GMChain` が独立して定義する。FayID は `GMChain` に対して読み取り専用の疎結合を維持し、ブラインドアンカー `gmcref_` のみを出力する。
4. **中央集権的本人確認（KYC）**：FayID 1.0 は、いかなる中央集権的レジストリやルート認証局も前提としない。

## 1.2 規定キーワードと日本語規範表現の対応（Normative）

本文書における英大文字キーワード `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY`、および `OPTIONAL` は、[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) および [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) に従って解釈される。上記の英単語がすべて大文字で記載されている場合、または下表で明示的に対応付けられた日本語規範表現が使用されている場合に限り、規定上の拘束力を持つ。

| RFC 2119 / RFC 8174 キーワード | 日本語規範表現 | 拘束セマンティクス |
| --- | --- | --- |
| `MUST` / `SHALL` / `REQUIRED` | **しなければならない** | プロトコル上の必須要件であり、違反は不適合実装となる |
| `MUST NOT` / `SHALL NOT` | **してはならない** | プロトコル上の絶対的禁止事項であり、違反は不適合実装となる |
| `SHOULD` / `RECOMMENDED` | **すべきである** | 十分に評価された正当な理由がない限り、従う必要がある |
| `SHOULD NOT` / `NOT RECOMMENDED` | **すべきではない** | 十分に評価された正当な理由がない限り、避ける必要がある |
| `MAY` / `OPTIONAL` | **してもよい** | 実装者の裁量に完全に委ねられ、相互運用する実装はその有無の双方に対応しなければならない |

## 1.3 中核用語定義（Normative）

実装および派生文書は以下の用語境界を厳格に遵守**しなければならない**（`MUST`）。

- **人間プライム（`Human Prime`）**：`HumanID`（`hid_`）によって識別され、個体デジタル分身を所有・制御する実在の自然人である。すべての仕様、実装、およびインターフェースにおいて自然人を指す場合は、統一して「人間プライム」（`Human Prime`）を使用し**なければならない**。
- **ホスト（`Host`）**：`Fay` インスタンスを収容・実行・マウントする端末デバイス、オペレーティングシステム環境、またはクライアントアプリケーション**のみ**を指す。実装および文書において、自然人または**人間プライム**を指すために「ホスト」または `Host` を使用**してはならない**。
- **Fay（`Fay = iFay + coFay`）**：iFay エコシステムにおいて検証可能なアイデンティティと説明責任の帰属を持つすべてのデジタル主体の総称であり、相互排他的な `iFay` と `coFay` の 2 つの部分集合のみから構成される。
  - **`iFay`（個体デジタル分身、`ifay_`）**：唯一の `HumanID` にバインドされる個人デジタル人格インスタンスであり、`HumanID : iFayID = 1:N` の譲渡不能なバインディングを満たす。
  - **`coFay`（共有ロールデジタル体、`cofay_`）**：協働、サービス、または公共機能向けのデジタルロールインスタンスであり、単一の `HumanID` または単一の `OrganizationID` に直接帰属し、所有権の移転と運用管理権限の分離をサポートする。
- **組織エンティティ（`OrganizationID`、`org_`）**：法的責任またはガバナンス上の責任を負う組織主体であり、自然人のガバナンス代表（`Steward`）を持ち、単一親・非巡回の組織階層ツリーに参加できる。
- **保持者エージェント（`Holder Agent`）**：**人間プライム**または組織の管理下で動作するローカル鍵管理および自己発行ソフトウェアコンポーネントであり、中央集権的なリモート機関ではなく、管理下の**ホスト**（端末デバイスまたはアプリケーション）内で実行される。
- **公誉チェーン（`GMChain`）および美誉値（`MeriToken`）**：`公誉チェーン`（英語略称 `GMChain`）はエコシステムにおける社会貢献を記録する公共レピュテーション台帳である。`美誉値`（`MeriToken`、計測単位 `Merit Unit`）は非貨幣的な社会貢献の評価指標であり、法定通貨への換金・マイニング発行・金融決済・投機的取引の性質を持たない。

## 1.4 プロトコルバージョンモデルとネゴシエーション規則（Normative）

### 1.4.1 直交する 3 つのバージョン軸

FayID は互いに混用されない 3 つのバージョン軸を厳格に区別する。

1. **プロトコルワイヤフォーマットバージョン（Protocol Version）**：2 セグメント形式の `MAJOR.MINOR`（FayID 1.0 では `"1.0"` に固定）を採用し、**`PATCH` セグメントは設けない**。ワイヤフォーマットのエンベロープフィールド `version` および JSON Schema の定数制約には、2 セグメント文字列 `"1.0"` のみが出現**しなければならない**（`MUST`）。
2. **文書ステータス（Document Status）**：仕様の成熟度（`Draft`、`Final` など）を示し、仕様文書のフロントマターメタデータにのみ記載される。プロトコルのワイヤフォーマットペイロードに含めては**ならない**（`MUST NOT`）。
3. **編集版次（Edition Date）**：`YYYY-MM-DD` 形式の日付識別子（本版次は `2025-10-25`）を採用し、仕様ディレクトリおよび Schema スナップショットパスのアーカイブ管理に用いられる。プロトコルのワイヤフォーマットペイロードに含めては**ならない**（`MUST NOT`）。

### 1.4.2 メジャー・マイナーバージョン進化の判定基準

- **マイナーバージョンアップグレード（`MINOR`）**：後方互換性を保つ増分拡張（任意のエンベロープフィールドの追加、目的別サブ鍵ドメイン定数の追加、任意のクレデンシャルメタデータの追加など）に限定される。旧バージョンの検証者は未知の任意フィールドを無視したうえで、通常どおり署名検証および妥当性検査を完了できる。
- **メジャーバージョンアップグレード（`MAJOR`）**：既存の識別子正規表現の変更、ハッシュまたは署名プリミティブの変更、HKDF ドメイン分離文字列の変更、既存の必須フィールドの意味的厳格化、またはカスケード失効の判定結果の変更を含むあらゆる破壊的変更では、`MAJOR` をインクリメント**しなければならない**（`MUST`）。
- **編集上の正誤表に関する制約**：同一 `MAJOR.MINOR` における編集版次の更新は明確化のための文言修正のみを許容し、適合性判定結果を変更する規範的変更を含めては**ならない**。

### 1.4.3 バージョンハンドシェイクと前方互換性

1. 通信双方が FayID レコードまたはレシートを交換する際、トップレベルまたは埋め込みの `version` フィールドを検証**しなければならない**（`MUST`）。FayID 1.0 に準拠するレコードでは、`version` は `"1.0"` と厳密に一致**しなければならない**（`MUST`）（`"1"`、`"1.0.0"`、`"v1.0"` は受理しない）。
2. 同一メジャーバージョン（`MAJOR = 1`）内で複数のマイナーバージョンをサポートする実装は、ハンドシェイクネゴシエーション時に双方が共通してサポートする最大の `1.x` マイナーバージョンを選択し、かつ `"1.0"` への後方互換性を維持**しなければならない**（`MUST`）。
3. 未知または非互換の `MAJOR` バージョンに遭遇した場合、検証者は直ちに処理を拒否**しなければならず**（`MUST`）、ダウングレード推測や署名検証の暗黙的なスキップを行っては**ならない**。
4. 検証者は同一 `MAJOR` のペイロードを解析する際、未認識の任意拡張フィールドを無視**しなければならない**（`MUST`）が、バイト単位での署名検証の一貫性を保証するため、JCS 署名の計算または検証時には署名対象オブジェクト内のすべての既存フィールドを保持**しなければならない**（`MUST`）。
5. プロトコルのマイナーバージョンアップグレードによって、それ以前に発行され有効期限内の `dyn_`、`grt_`、または `vrf_` クレデンシャルを早期失効させては**ならない**（`MUST NOT`）。
