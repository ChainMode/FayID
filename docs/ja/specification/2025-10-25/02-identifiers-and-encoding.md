# 第 2 章 識別子構文、エンコーディングおよびリソース参照仕様

## 2.1 8 種類の規定識別子プレフィックス一覧（Normative）

すべての FayID 暗号学的識別子および派生クレデンシャル文字列は `<prefix>_<body>` 構造を採用**しなければならない**（`MUST`）。人間可読な小文字の組織識別子文字集合 `[a-z0-9-]+` を許容する `org_` を除き、残り 7 種類の識別子本体は**小文字・`=` パディングなしの RFC 4648 Base32** 文字集合（`[a-z2-7]+`）を採用**しなければならない**（`MUST`）。

| 型定数 | 文字列プレフィックス | 本体正規表現 | 代表的なバイト長とセマンティクス |
| --- | --- | --- | --- |
| `HUMAN_ID` | `hid_` | `^[a-z2-7]+$` | `SHA-256(humanPublicKey)`（32 バイト → Base32 で 52 文字）、**人間プライム**のルート ID 識別子 |
| `IFAY_ID` | `ifay_` | `^[a-z2-7]+$` | `SHA-256("ifay:" \|\| humanId \|\| ":" \|\| publicKey)`（32 バイト）、個人デジタル分身識別子 |
| `COFAY_ID` | `cofay_` | `^[a-z2-7]+$` | `SHA-256("cofay:" \|\| ownerId \|\| ":" \|\| publicKey)`（32 バイト）、共有ロールデジタル体識別子 |
| `ORGANIZATION_ID` | `org_` | `^[a-z0-9-]+$` | 組織主体識別子（決定論的ハッシュ本体または正規化された組織短縮名をサポート） |
| `DYNAMIC_CODE` | `dyn_` | `^[a-z2-7]+$` | 20 バイトの HMAC 切り詰めタグ（Base32 で 32 文字）、短命・非リンク型提示トークン |
| `VERIFICATION_CODE` | `vrf_` | `^[a-z2-7]+$` | 20 バイトの検証レシートダイジェスト、`grt_` または `cofay_` の状態検証結果にバインド |
| `AUTHORIZATION_GRANT` | `grt_` | `^[a-z2-7]+$` | 20 バイトのスコープ付き従来型クレデンシャル交換認可識別子 |
| `OPAQUE_REF` | `gmcref_` | `^[a-z2-7]+$` | 32 バイトのブラインド自然人アンカー（Base32 で 52 文字）、`GMChain` ガバナンス重複排除専用 |

さらに、`iFay` 登録レコードおよびオフラインパッケージにおいて平文の `hid_` の代替として用いられる一方向コミットメントは、`hidproof_<lowercase-base32-nopad>` 形式（正規表現 `^hidproof_[a-z2-7]{16,}$`）を採用する。

## 2.2 正規化および厳格拒否規則（Normative）

解析関数 `normalizeFayID(input)` は以下の決定論的規則を満たさ**なければならない**（`MUST`）。

1. **型および非空検査**：非文字列入力または空文字列に対しては、直ちにエラーコード `MALFORMED_FAYID_STRING` を返さ**なければならない**（`MUST`）。
2. **大文字・小文字の折り畳み**：パーサは ASCII 大文字を小文字に折り畳んでから（`input.toLowerCase()`）、上表の 8 種類のプレフィックスと照合**しなければならない**（`MUST`）。
3. **厳格拒否（暗黙的修復の禁止）**：パーサは、先頭・末尾の空白文字の自動トリミング、ハイフンの除去（`org_` 本体における正当なハイフンを除く）、`=` パディング文字の除去、または紛らわしい文字の置換（`0`/`1`/`8`/`9` を Base32 文字へ置換するなど）を行っては**ならない**。空白、`=`、未知のプレフィックス、空の本体、または範囲外の文字（例えば `hid_` 本体における `0`、`1`、`8`、`9` の出現）を含む文字列は、すべて一律に拒否して `MALFORMED_FAYID_STRING` を返さ**なければならない**（`MUST`）。
4. **ラウンドトリップ不変条件（Round-Trip Invariant）**：任意の正当な正規化済み識別子 `x` に対して再度 `normalizeFayID(x)` を実行した場合、`ok: true` かつ `value.canonical === x` を返さ**なければならない**（`MUST`）。また、任意のバイト配列 `b` に対してパディングなし小文字 Base32 エンコードを行った後にデコードした場合、バイト単位で `b` を完全に復元**しなければならず**（`MUST`）、末尾のゼロ詰めパディングビットはすべて `0` で**なければならない**（`MUST`）（非ゼロの余剰ビットが存在する場合はデコードを拒否**しなければならない**（`MUST`））。

## 2.3 `resourceRef` リソース名前空間とスコープマッチング（Normative）

認証交換における対象リソースは `resourceRef` によって識別される。`normalizeResourceRef(input)` および `matchesResourceRef(grantedResourceRef, requestedResourceRef, scopeMode)` は以下の規則に従わ**なければならない**（`MUST`）。

1. **構文構造**：`resourceRef` は `<namespace>:<path>` 構造を採用する。
   - `<namespace>` は小文字への折り畳み後に `^[a-z][a-z0-9+.-]*$` と一致**しなければならない**（`MUST`）。
   - `:` の右側の `<path>` は非空であり、いかなる空白文字も含まず、`/` で終わらず（1 文字のルートパスを除く）、かつ空のパスセグメント（`//`）や相対トラバーサルセグメント（`.` または `..`）を含んでは**ならない**。
   - 上記のいずれかの条件に違反した場合は、`MALFORMED_FAYID_STRING` を返さ**なければならない**（`MUST`）。
2. **大文字・小文字の区別**：`<namespace>` 部分は小文字に正規化されるが、`:` の右側の `<path>` は元の大文字・小文字を保持**しなければならない**。
3. **スコープマッチングモード（`scopeMode`）**：
   - `EXACT`（デフォルト）：正規化後の `requestedResourceRef === grantedResourceRef` が成り立つ場合にのみ一致とみなす。
   - `PREFIX`：正規化後の要求リソースが認可リソース自体と等しい場合、または `/` パスセグメント境界上で認可リソースをプレフィックスとして持つ場合（すなわち `requested.startsWith(granted + "/")`）にのみ一致とみなす。例えば、認可 `cap:repo/fayid` は `PREFIX` モードにおいて `cap:repo/fayid/issues` と一致するが、兄弟パスである `cap:repo/fayid-ext` とは**決して一致しない**（文字列プレフィックスによる権限逸脱の防止）。

## 2.4 レガシー 64 桁 16 進数公開鍵識別子のブリッジ（Normative）

32 バイトの生 Ed25519 公開鍵の 16 進数文字列（64 桁の 16 進文字）のみを保持する初期の既存レコードとの互換性を確保するため、ツールキットは明示的なブリッジ関数 `adaptLegacyHexIdentifier(hex64, prefix)` を提供する。

1. 入力 `hex64` は空白除去後に `^[0-9a-fA-F]{64}$` と厳密に一致**しなければならず**（`MUST`）、対象 `prefix` は `hid_`、`ifay_`、または `cofay_` のみを許容し、それ以外は `MALFORMED_FAYID_STRING` を返す。
2. ブリッジ処理はデコード後の 32 バイト生公開鍵に対して `SHA-256` を計算し、`<prefix><base32-nopad>` にエンコードする。これはネイティブのルート ID 計算式と完全に同一である。
3. プロトコルの正式なワイヤフォーマットペイロード内で、生の 64 桁 16 進数文字列を FayID として直接伝送**してはならない**。ブリッジ変換はプロトコル境界に入る前に明示的に完了させる必要がある。
