# Глава 3. Суверенный криптографический набор и деривация целевых подключей

## 3.1 Суверенная модель доверия `Holder-of-Key` (нормативный раздел)

FayID 1.0 опирается исключительно на суверенную модель доверия владения ключом (`Holder-of-Key`):

1. Создание идентичности и управление ею зависят только от криптографического доказательства владения соответствующим закрытым ключом Ed25519 без какой-либо опоры на подписи централизованных эмитентов.
2. Каждая изменяющая состояние операция, заявляющая полномочия над `HumanID`, `iFayID`, `coFayID` или `OrganizationID` (регистрация, делегирование менеджеров, присоединение к иерархии, передача владения или отзыв), `ДОЛЖНА` содержать действительную подпись управляющей ключевой пары; запросы с отсутствующими или недействительными доказательствами `ДОЛЖНЫ` отклоняться с кодом ошибки `HUMAN_ID_OWNERSHIP_NOT_PROVEN`, `OWNERSHIP_NOT_PROVEN` или `TARGET_OWNERSHIP_NOT_PROVEN`.

## 3.2 Обязательные криптографические примитивы (нормативный раздел)

FayID 1.0 стандартизирует открытые криптографические примитивы, доступные без проприетарных внешних зависимостей:

| Назначение | Обязательный примитив | Канонический размер выхода |
| --- | --- | --- |
| Асимметричные подписи и доказательства `Holder-of-Key` | Ed25519 (RFC 8032 PureEdDSA) | 32-байтовый открытый ключ, 64-байтовая подпись |
| Дайджесты идентификаторов и обязательства с солью | SHA-256 (FIPS 180-4) | 32-байтовый дайджест |
| Детерминированная деривация целевых подключей | HKDF-SHA256 (RFC 5869) | 32-байтовый производный сид |
| Хеширование унаследованных субъектов и MAC динамических кодов | HMAC-SHA256 (RFC 2104) | 32-байтовый MAC (усекаемый до 20 байтов в оговорённых случаях) |
| Канонические полезные нагрузки JSON для подписи | JCS (RFC 8785 JSON Canonicalization Scheme) | Детерминированная последовательность байтов UTF-8 |

Исходная энтропия входных значений `masterSeed` и `userBlindSalt` `ДОЛЖНА` составлять не менее **256 бит (32 байтов)**; входные данные короче 32 байтов `ДОЛЖНЫ` отклоняться с ошибкой `INSUFFICIENT_ENTROPY`.

## 3.3 Доменно-разделённые целевые подключи HKDF-SHA256 (нормативный раздел)

Чтобы мастер-сиды и корневые закрытые ключи никогда не попадали в высокочастотные контуры подписи или исходящие архивные пакеты, `Holder Agent` `ДОЛЖЕН` выводить криптографически изолированные 32-байтовые целевые подключи из мастер-сида (`>= 32` байтов) с помощью HKDF-SHA256:

```text
subkeySeed32 = HKDF-SHA256(
  ikm  = masterSeedBytes,
  salt = SHA-256(UTF8("fayid.subkey.salt:" || domain)),
  info = UTF8(domain || ":" || context),
  len  = 32
)
```

FayID 1.0 определяет пять нормативных констант `SubkeyDomain`:

| Константа | Строка разделения доменов (`domain`) | Назначение и граница безопасности |
| --- | --- | --- |
| `ENTITY` | `ifay.fayid.entity.v1` | Выводит ключевые пары Ed25519 управления сущностями для `HumanID`, `iFay`, `coFay` и `OrganizationID` |
| `EGO_PACKAGE_SIGNING` | `ifay.ego.package-signing.v1` | Выделенный подключ подписи Ed25519 исключительно для исходящих пакетов персоны и состояния `.ego` |
| `DYNAMIC_CODE` | `ifay.fayid.dynamic-code.v1` | Выводит симметричный ключевой материал для контекстов выпуска и проверки динамических кодов (`dyn_`) |
| `AUTH_EXCHANGE` | `ifay.fayid.auth-exchange.v1` | Выводит ключевой материал подписи для разрешений авторизации (`grt_`) и квитанций проверки (`vrf_`) |
| `GMC_NATURAL_PERSON` | `ifay.gmc.natural-person.v1` | Выводит псевдослучайный ключевой материал для слепых якорей физических лиц (`gmcref_`) в `GMChain` |

Реализации `ДОЛЖНЫ` обеспечивать два жёстких инварианта изоляции:

1. **Обязательное разделение доменов**: вызовы деривации подключей `ДОЛЖНЫ` передавать непустые строки `domain` и `context`, где `domain` принадлежит зарегистрированному набору `SubkeyDomain`; вызовы с отсутствующим или нераспознанным доменом `ДОЛЖНЫ` завершаться ошибкой `DOMAIN_SEPARATION_REQUIRED`.
2. **Нулевое раскрытие корневых ключей в исходящих пакетах Ego**: исходящие пакеты `.ego` `ДОЛЖНЫ` подписываться исключительно подключом, выведенным в домене `ifay.ego.package-signing.v1`, формируя конверт подписи с полями `version: "1.0"`, `domain: "ifay.ego.package-signing.v1"`, `signerFayId`, `keyId`, `signingPublicKeyHex`, `manifestDigestSha256`, `signedAt` и `signatureHex`. Исходящие пакеты, публичные записи сущностей и квитанции проверки `НЕ ДОЛЖНЫ` содержать поля `masterSeed`, `seed`, `privateKey`, `secretKey` или `mnemonic`; проверяющие стороны `ДОЛЖНЫ` отклонять любой конверт, содержащий материал закрытого ключа.

## 3.4 Правила канонической подписи RFC 8785 JCS (нормативный раздел)

Каждая структурированная полезная нагрузка, проверяемая между реализациями (доказательства привязки владения, взаимные согласия на иерархию, подписываемые манифесты пакетов Ego и полезные нагрузки квитанций проверки `vrf_`), перед формированием или проверкой подписи Ed25519 либо хешированием SHA-256 `ДОЛЖНА` сериализоваться в детерминированную последовательность байтов UTF-8 согласно RFC 8785 JCS:

1. Имена свойств объектов сортируются в порядке возрастания кодовых единиц UTF-16, а свойства со значением `undefined` опускаются;
2. Конечные числа записываются в минимальном десятичном представлении ECMAScript (`-0` сериализуется как `"0"`, а `NaN` и `Infinity` отклоняются);
3. Порядок элементов массивов сохраняется без изменений, строки используют минимальное стандартное экранирование JSON, а незначащие пробельные символы между лексемами не выводятся.
