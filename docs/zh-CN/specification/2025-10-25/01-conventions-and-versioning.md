# 第 1 章 规范约定、核心术语与版本治理

## 1.1 适用范围与非目标

FayID 1.0 定义了 iFay 生态内的自主权身份标识、目的子密钥派生、实体所有权与组织层级不变量、不可关联动态码、传统凭据鉴权兑换、级联吊销，以及面向`公誉链`（`GMChain`）的隐私保护自然人锚点。

以下事项明确不在本协议范围内：

1. **传输与会话握手协议**：跨智能体通信报文封装与会话安全由 Faying 协议族定义，FayID 仅提供身份原语、签名信封与核验回执。
2. **运行时生命周期调度**：`iFay` 与 `coFay` 在终端设备上的进程编排由 FayGer 运行时负责。
3. **声誉记账与治理权重计算**：`美誉值`（`MeriToken`）的累积与治理计量由 `GMChain` 独立定义。FayID 对 `GMChain` 保持只读解耦，仅输出盲化锚点 `gmcref_`。
4. **中心化实名核验（KYC）**：FayID 1.0 不预设任何中心化注册局或根证书颁发机构。

## 1.2 规范性关键词与中文动词映射（Normative）

本文档中的英文大写关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY` 与 `OPTIONAL` 按照 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 及 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) 解释；仅当上述英文词全部大写，或使用下表显式映射的中文规范性动词时，才具有规范性约束力：

| RFC 2119 / RFC 8174 关键词 | 中文规范性对应表述 | 约束语义 |
| --- | --- | --- |
| `MUST` / `SHALL` / `REQUIRED` | **必须** | 协议强制要求，违反即构成不一致实现 |
| `MUST NOT` / `SHALL NOT` | **严禁** / **不得** | 协议绝对禁止，违反即构成不一致实现 |
| `SHOULD` / `RECOMMENDED` | **应当** | 除非存在经充分评估的特定理由，否则应予遵循 |
| `SHOULD NOT` / `NOT RECOMMENDED` | **不应** | 除非存在经充分评估的特定理由，否则应予避免 |
| `MAY` / `OPTIONAL` | **可以** / **可选** | 完全由实现方自主决定，互操作方必须兼容其存在或缺省 |

## 1.3 核心术语定义（Normative）

实现与衍生文档 `MUST` 严格遵循以下术语边界：

- **人类原型（`Human Prime`）**：由 `HumanID`（`hid_`）标识、拥有并控制个体数字分身的真实自然人。所有规范、实现与接口在指代自然人时**必须**统一使用“人类原型”（`Human Prime`）。
- **宿主（`Host`）**：**仅**指承载、运行或挂载 `Fay` 实例的终端设备、操作系统环境或客户端应用程序。实现与文档**严禁**使用“宿主”或 `Host` 指代自然人或**人类原型**。
- **Fay（`Fay = iFay + coFay`）**：iFay 生态中所有具备可验证身份与问责归属的数字主体统称，且仅由 `iFay` 与 `coFay` 两类互斥子集构成：
  - **`iFay`（个体数字分身，`ifay_`）**：绑定至唯一 `HumanID` 的个人数字人格实例，满足 `HumanID : iFayID = 1:N` 不可转让绑定。
  - **`coFay`（共享角色数字体，`cofay_`）**：面向协作、服务或公共职能的数字角色实例，直接归属于单一 `HumanID` 或单一 `OrganizationID`，支持所有权变更与运维管理授权分离。
- **组织实体（`OrganizationID`，`org_`）**：承担法律或治理责任的组织主体，具备自然人治理代表（`Steward`），可加入单父无环组织层级树。
- **持有者代理（`Holder Agent`）**：在**人类原型**或组织控制下的本地密钥管理与自签发软件组件，运行于受控**宿主**（终端设备或应用）内，而非中心化远程机构。
- **公誉链（`GMChain`）与美誉值（`MeriToken`）**：`公誉链`（英文简称 `GMChain`）是记录生态社会贡献的公共声誉账本；`美誉值`（`MeriToken`，计量单位 `Merit Unit`）是非货币化的社会贡献度量指标，不具备法币兑换、挖矿发行、金融结算或投机交易属性。

## 1.4 协议版本模型与协商规则（Normative）

### 1.4.1 三条正交版本轴

FayID 严格区分三条互不混用的版本轴：

1. **协议线格式版本（Protocol Version）**：采用两段式 `MAJOR.MINOR` 格式（FayID 1.0 固定为 `"1.0"`），**不设 `PATCH` 段**。只有两段式 `"1.0"` 字符串 `MUST` 出现在线格式信封字段 `version` 与 JSON Schema 常量约束中。
2. **文档状态（Document Status）**：标记规范成熟度（如 `Draft`、`Final`），仅出现在规范文档扉页元数据中，`MUST NOT` 进入协议线格式载荷。
3. **编辑版次（Edition Date）**：采用 `YYYY-MM-DD` 日期标识（本版次为 `2025-10-25`），用于归档规范目录与 Schema 快照路径，`MUST NOT` 进入协议线格式载荷。

### 1.4.2 主次版本演进判据

- **次版本升级（`MINOR`）**：仅限向后兼容的增量扩展（例如新增可选信封字段、新增目的子密钥域常量或新增可选凭据元数据）。旧版验证方忽略未知可选字段后仍可正常完成验签与校验。
- **主版本升级（`MAJOR`）**：任何破坏性变更（包括修改既有标识符正则、变更哈希或签名原语、改变 HKDF 域分离字符串、收紧既有必填字段语义或改变级联吊销判定结果）`MUST` 递增 `MAJOR`。
- **编辑勘误约束**：同一 `MAJOR.MINOR` 下的编辑版次更新仅允许澄清性文字修订，**不得**夹带任何改变合规判定结果的规范性变更。

### 1.4.3 版本握手与前向兼容

1. 通信双方在交换 FayID 记录或回执时，`MUST` 校验顶层或内嵌 `version` 字段。对于符合 FayID 1.0 的记录，`version` `MUST` 精确等于 `"1.0"`（不接受 `"1"`、`"1.0.0"` 或 `"v1.0"`）。
2. 同主版本（`MAJOR = 1`）内支持多个次版本的实现，在握手协商时 `MUST` 选择双方共同支持的最高 `1.x` 次版本，并向下兼容至 `"1.0"`。
3. 遇到未知或不兼容的 `MAJOR` 版本时，验证方 `MUST` 立即拒绝处理，**严禁**降级猜测或静默跳过签名验证。
4. 验证方在解析同 `MAJOR` 载荷时 `MUST` 忽略未识别的可选扩展字段，但计算或核验 JCS 签名时 `MUST` 保留被签名对象内的全部既有字段，以保证字节级验签一致性。
5. 协议次版本平滑升级 `MUST NOT` 使此前已签发且尚未过期的 `dyn_`、`grt_` 或 `vrf_` 凭据提前失效。
