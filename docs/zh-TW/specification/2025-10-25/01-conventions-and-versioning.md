# 第 1 章 規範約定、核心術語與版本治理

## 1.1 適用範圍與非目標

FayID 1.0 定義了 iFay 生態系內的自主權身分識別、目的子金鑰派生、實體所有權與組織層級不變量、不可關聯動態碼、傳統憑證鑑權兌換、連鎖撤銷，以及面向`公譽鏈`（`GMChain`）的隱私保護自然人錨點。

以下事項明確不在本協定範圍內：

1. **傳輸與工作階段交握協定**：跨智慧體通訊封包封裝與工作階段安全由 Faying 協定族定義，FayID 僅提供身分原語、數位簽章信封與核驗回執。
2. **執行階段生命週期排程**：`iFay` 與 `coFay` 在終端裝置上的行程編排由 FayGer 執行環境負責。
3. **聲譽記帳與治理權重計算**：`美譽值`（`MeriToken`）的累積與治理計量由 `GMChain` 獨立定義。FayID 對 `GMChain` 保持唯讀解耦，僅輸出盲化錨點 `gmcref_`。
4. **中心化實名查驗（KYC）**：FayID 1.0 不預設任何中心化註冊機構或根憑證授權機構（CA）。

## 1.2 規範性關鍵字與中文動詞對應（Normative）

本文件中的英文大寫關鍵字 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、`RECOMMENDED`、`NOT RECOMMENDED`、`MAY` 與 `OPTIONAL` 依據 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 及 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) 解釋；僅當上述英文詞全部大寫，或使用下表顯式對應的中文規範性動詞時，才具有規範性約束力：

| RFC 2119 / RFC 8174 關鍵字 | 中文規範性對應表述 | 約束語義 |
| --- | --- | --- |
| `MUST` / `SHALL` / `REQUIRED` | **必須** | 協定強制要求，違反即構成不一致實作 |
| `MUST NOT` / `SHALL NOT` | **嚴禁** / **不得** | 協定絕對禁止，違反即構成不一致實作 |
| `SHOULD` / `RECOMMENDED` | **應當** | 除非存在經充分評估的特定理由，否則應予遵循 |
| `SHOULD NOT` / `NOT RECOMMENDED` | **不應** | 除非存在經充分評估的特定理由，否則應予避免 |
| `MAY` / `OPTIONAL` | **可以** / **可選** | 完全由實作方自主決定，互通方必須相容其存在或省略 |

## 1.3 核心術語定義（Normative）

實作與衍生文件 `MUST` 嚴格遵循以下術語邊界：

- **人類原型（`Human Prime`）**：由 `HumanID`（`hid_`）識別、擁有並控制個體數位分身的真實自然人。所有規範、實作與介面在指稱自然人時**必須**統一使用「人類原型」（`Human Prime`）。
- **宿主（`Host`）**：**僅**指承載、執行或掛載 `Fay` 實例的終端裝置、作業系統環境或用戶端應用程式。實作與文件**嚴禁**使用「宿主」或 `Host` 指稱自然人或**人類原型**。
- **Fay（`Fay = iFay + coFay`）**：iFay 生態系中所有具備可驗證身分與問責歸屬的數位主體統稱，且僅由 `iFay` 與 `coFay` 兩類互斥子集構成：
  - **`iFay`（個體數位分身，`ifay_`）**：綁定至唯一 `HumanID` 的個人數位人格實例，滿足 `HumanID : iFayID = 1:N` 不可轉讓綁定。
  - **`coFay`（共享角色數位體，`cofay_`）**：面向協作、服務或公共職能的數位角色實例，直接歸屬於單一 `HumanID` 或單一 `OrganizationID`，支援所有權變更與維運管理授權分離。
- **組織實體（`OrganizationID`，`org_`）**：承擔法律或治理責任的組織主體，具備自然人治理代表（`Steward`），可加入單父無環組織層級樹。
- **持有者代理（`Holder Agent`）**：在**人類原型**或組織控制下的本機金鑰管理與自簽發軟體元件，執行於受控**宿主**（終端裝置或應用程式）內，而非中心化遠端機構。
- **公譽鏈（`GMChain`）與美譽值（`MeriToken`）**：`公譽鏈`（英文簡稱 `GMChain`）是記錄生態系社會貢獻的公共聲譽帳本；`美譽值`（`MeriToken`，計量單位 `Merit Unit`）是非貨幣化的社會貢獻度量指標，不具備法幣兌換、挖礦發行、金融結算或投機交易屬性。

## 1.4 協定版本模型與協商規則（Normative）

### 1.4.1 三條正交版本軸

FayID 嚴格區分三條互不混用的版本軸：

1. **協定線格式版本（Protocol Version）**：採用兩段式 `MAJOR.MINOR` 格式（FayID 1.0 固定為 `"1.0"`），**不設 `PATCH` 段**。只有兩段式 `"1.0"` 字串 `MUST` 出現在線格式信封欄位 `version` 與 JSON Schema 常數約束中。
2. **文件狀態（Document Status）**：標記規範成熟度（如 `Draft`、`Final`），僅出現在規範文件扉頁詮釋資料中，`MUST NOT` 進入協定線格式酬載。
3. **編輯版次（Edition Date）**：採用 `YYYY-MM-DD` 日期識別（本版次為 `2025-10-25`），用於歸檔規範目錄與 Schema 快照路徑，`MUST NOT` 進入協定線格式酬載。

### 1.4.2 主次版本演進判準

- **次版本升級（`MINOR`）**：僅限向下相容的增量擴充（例如新增可選信封欄位、新增目的子金鑰域常數或新增可選憑證詮釋資料）。舊版驗證方忽略未知可選欄位後仍可正常完成驗章與校驗。
- **主版本升級（`MAJOR`）**：任何破壞性變更（包括修改既有識別碼正規表示式、變更雜湊或數位簽章原語、改變 HKDF 域分離字串、收緊既有必填欄位語義或改變連鎖撤銷判定結果）`MUST` 遞增 `MAJOR`。
- **編輯勘誤約束**：同一 `MAJOR.MINOR` 下的編輯版次更新僅允許澄清性文字修訂，**不得**夾帶任何改變合規判定結果的規範性變更。

### 1.4.3 版本交握與前向相容

1. 通訊雙方在交換 FayID 紀錄或回執時，`MUST` 校驗頂層或內嵌 `version` 欄位。對於符合 FayID 1.0 的紀錄，`version` `MUST` 精確等於 `"1.0"`（不接受 `"1"`、`"1.0.0"` 或 `"v1.0"`）。
2. 同主版本（`MAJOR = 1`）內支援多個次版本的實作，在交握協商時 `MUST` 選擇雙方共同支援的最高 `1.x` 次版本，並向下相容至 `"1.0"`。
3. 遇到未知或不相容的 `MAJOR` 版本時，驗證方 `MUST` 立即拒絕處理，**嚴禁**降級猜測或靜默跳過數位簽章驗證。
4. 驗證方在解析同 `MAJOR` 酬載時 `MUST` 忽略未識別的可選擴充欄位，但計算或核驗 JCS 數位簽章時 `MUST` 保留被簽署物件內的全部既有欄位，以保證位元組級驗章一致性。
5. 協定次版本平滑升級 `MUST NOT` 使此前已簽發且尚未過期的 `dyn_`、`grt_` 或 `vrf_` 憑證提前失效。
